# PART A · Program length planner (planner §1; follow exactly)

## A1. What the coach enters (builder, before Build)
Per planner §1a:
- **Program length:** Start date + End date, **or** Start date + number of weeks (1–52). Default: start = next Monday, 8 weeks.
- **What happens at the end** (one choice): **Season starts · Testing day · Break · Nothing special.** If the team calendar has the season's first match, suggest it as the end date.
- Everything already in the builder still applies (Week setup card, session length, equipment, level mix, combined calendar).

## A2. How Approach plans it
Planner §1b steps 1–6 and the §1c tables, exactly:
1. **Phase by date** from the calendar (off-season / preseason / in-season / post-season); club matches still switch to Maintain.
2. **Anchor the end** by end type (Season starts: last 1–2 weeks Power, final week −30% volume; Testing day: last week deload with the test on its last lift day; Break: normal last week; Nothing special: no taper).
3. **Fill backward** with the §1c block sequence so the program ends on the right block.
4. **Deloads** end every block except the one right before the taper week; never more than 4 loading weeks in a row.
5. **Testing suggestions:** end of week 1 (baseline, if no result in the last 12 weeks) and the last week when the end is Testing day or Season starts. **Existing testing rules unchanged** (≥ 48 h before a match on the combined calendar, supervision lock, eligibility, D-020).
6. **Breaks inside the window:** the block pauses; after 14+ days it restarts at week 1 and the plan re-flows to the same end date, **shortening Accumulation first**.
- **§1c wins over §1b where they differ (D-068.1).** Example: the 8-week Season-starts plan is Accumulation 3 → Strength 3 → Power 2 (no Strength-Power), as the table and the §4 criterion say.
- Weeks between table rows: the extra week goes to the **earliest** block; remove weeks from Accumulation first, then Strength-Power. **No block under 2 weeks.**
- Other phases (preseason, in-season, post-season, plans that span phases) per the §1c "Other phases" table.

## A3. What the coach sees
Per planner §1d: the **plan timeline** (one row per week: date, block, "Strength · week 2 of 4," deload/taper/testing markers, the week's day kinds), the one-line plan summary, rebuild on change (generated sessions only), and the end prompt *"Varsity's program ended Jan 24. Build the next one?"* pre-filled with the next phase. Screens: UX `user-flows-planner-v3.md`.

## A4. Data
`program.blockStart` (existing) is the start date; **`program.endDate`** and **`program.endType`** are new (§4). Each week's block is written into the existing per-week/session keys (`block`, as 2.4.0/2.4.1 do); no stored copy of the timeline.

## Part A acceptance criteria (planner §4 "Program length," copied exactly)
- [ ] The coach can set start + end date or start + weeks, and an end type; the plan view shows every week's block, deloads, taper, and suggested testing days.
- [ ] An 8-week off-season plan ending at "Season starts" is Accumulation 3 → Strength 3 → Power 2 with the last week at −30% volume; an 8-week plan ending at "Nothing special" is Accumulation 4 → Strength 4.
- [ ] A plan that crosses the first practice switches to preseason Power at that date; one that crosses the first match switches to Maintain.
- [ ] A coach break inside the window re-flows the plan to still end on the end date, shortening Accumulation first; no block under 2 weeks.
- [ ] Rebuilding after a date change only changes generated sessions.
- [ ] *(Product)* Every row of the §1c off-season table (1–17+ weeks, both end-type columns) and the "Other phases" table produces its listed blocks; in-between lengths add the extra week to the earliest block.
- [ ] *(Product)* Testing day end: the last week is a deload with the suggested test on its last lift day; suggested testing days never fall within 48 h of a match on the combined calendar (another team's included, without showing it to the coach) and keep the supervision lock and eligibility rules.
- [ ] *(Product)* A program saved before 2.4.2 (no `endDate`) keeps its rolling blocks unchanged; the end prompt shows once the end date passes.

# PART B · "Your weight room" setup step and style suggestion (planner §2a; follow exactly)

## B1. The setup step (after Week setup, before Build)
1. **Racks or platforms:** 0–12, pre-filled from the team's rack groups.
2. **Equipment:** the existing picker, pre-filled.
3. **Athletes per session:** pre-filled from the roster; the coach can lower it.
4. **Session length:** pre-filled (§4a; existing `sessionMinutes`).
5. **Style:** Approach's suggestion with its reason line; the coach can pick Standard, Stations, or Rack rotation. Never blocked (D-045).

## B2. Suggestion table (confirmed by Product, D-065)
| Room | Suggested | Reason shown (exact) |
|---|---|---|
| Racks = 0 | **Stations** | "No racks, so groups rotate through equipment stations." |
| ≤ 2 athletes per rack | **Standard** | "Two or fewer per rack, so everyone works through their own sets." |
| **3–5 athletes per rack** | **Rack rotation** | "3–5 per rack, so each group rotates at its rack and nobody waits." |
| 6+ athletes per rack | **Stations** | "More than 5 per rack, so groups move between racks and other stations." |
| Session length < 30 min (any room) | the row above, plus **Express** sessions | "Short sessions: the essentials only." |
- **Athletes per rack** = athletes per session ÷ racks, **rounded up** (D-065).
- **Athletes per session isn't stored** (a setup input only; pre-filled from the roster each time). The rack count comes from the existing rack groups.

## B3. What choosing a style does
- **Rack rotation** creates rack groups **if none exist**, using the existing **balanced mix** auto-assign (D-026 rules: roster, level, and position only; never test results, loads, check-ins, bodyweight, or age; neutral names). Group sizes per §2d (3–5; 4 by default). If rack groups already exist, they're used as they are.
- **Outside 3–5 per rack** (the coach picks Rack rotation anyway, D-068.3): ≤ 2 per rack uses the groups-of-3 layout; 6+ uses the groups-of-5 layout, with extra athletes doubling up on non-rack, non-spot positions. Training to confirm; not in the stop rule.
- **Stations** uses the existing stations format and auto-build (`circuits-and-stations.md` Part 2; Part 1 together). With 0 racks, the existing "Start stations" grouping flow applies.
- **Home workout and mobility days are always Standard**; the chosen style applies to weight-room days only.
- The choice is stored as **`program.generatedFormat`** (§4) and restores itself when the program is edited. Changing one session's format later makes that session `'coach'`.

## Part B acceptance criteria (planner §4, first "Rack-aware generation" item, copied exactly)
- [ ] Setup asks racks, equipment, athletes per session, and length, and suggests the style per the §2a table with its reason; the coach can pick another.
- [ ] *(Product)* Choosing Rack rotation with no rack groups creates balanced-mix groups of 3–5 using only roster, level, and position; existing groups are left as they are.
- [ ] *(Product)* `generatedFormat` restores on edit; athletes per session is not stored anywhere on the server.

# PART C · Rack-aware generation (planner §2b–§2d; follow exactly)

## C1. Compiling a template day into rotations
Planner §2b steps 1–8 exactly, for every weight-room session when `generatedFormat = 'rack_rotation'`:
- **R1 Power** (A-block + fillers) → **R2 Strength** (B-block lift + spotter + fillers) → **R3 Secondary** (C and D blocks + fillers) → **cooldown** (Part D). Core and E-block items become the fillers.
- **Positions = the rack group's size** (3–5; 4 by default).
- **One rack, one bar per rotation (MUST):** at most one position uses the rack (squat, bench, or the rack's pull-up bar; assume the pull-up bar is on the rack) and at most one uses the group's barbell. If a template puts two in one rotation, the lower-priority item **moves to another rotation** where the rack/bar is free; if none, it switches **within its own ladder** to the nearest non-rack rung.
- **Spotter** right after barbell squat or bench (on by default). **The position before the rack lift** is upper body, core, shoulder, or mobility.
- **Rotation time** = longest position's work + 20 s, rounded to 15 s, raised until rack-lift rest meets the floors (tier A ≥ 2:00, tier P ≥ 1:30). **Rounds** = the rack lift's prescribed sets; **round 1 is the build-up round** for tier A and Olympic lifts (about 50–65%).
- **Fitting (D-068.4):** rotation sessions fit by §2b step 8 (drop rounds, never below 3 for the main lift counting the build-up round, then the lowest-priority filler). Rest is never shortened. The §4a trim order stays for Standard sessions. Each fit is logged in `fitLog` with undo, as today.
- Level switches apply per athlete at every position (§4b rule 8); R-1, R-2, and R-4 run on rotation sessions as on Standard ones.
- Data: the existing `Session.format: 'rack_rotation'` and `rotation` keys (2.4.0). Nothing new.

## C2. Compiled templates (acceptance examples)
Planner §2c tables are the expected output: **Day 1 Total: squat** and **Day 2 Total: hinge** (2-day off-season, groups of 4), and **in-season Day 1 Heavy**. Other templates (3-, 4-, 5-day, preseason, post-season) compile by the §2b rules.
**How the §2c check is run (D-068.2, founder's answer 11/20):**
- **Room:** a **full weight room** (rack with pull-up bar per group, barbell, bench, trap bar, dumbbells, kettlebells, boxes, med balls, bands). The §2c tables are checked as written in that room.
- **Second check, the 11/18 room** (program-design §4b list: rack with pull-up bar, barbell and bumpers, dumbbells, kettlebells, plyo boxes; no bench, bands, med balls, or trap bar): the same rotations generate, and each slot switches **down its own ladder** (e.g., Trap Bar Deadlift → RDL per the §2c note, Pallof → Dead Bug, med-ball throw → a jump, Bench Press → its equipment-fitting rung), with the one-rack/one-bar rule still holding.
- **"Generates the tables" means:** the same exercises in the same rotations and positions, with the rotation times as written. Rounds may be lower than the table **only** by §2b step 8 fitting at the coach's session length, logged in `fitLog`. *(Product note for Training: with the full warm-up, the Day 1 and Day 2 tables come to about 64–66 min, so at a 60-min target one round is fitted. Please check the arithmetic.)*

## C3. Group size and equipment variations
Planner §2d exactly: groups of 3 drop position 4 (keep the spotter; rack-lift rest = 2 × rotation time, still ≥ floors); groups of 5 put 2 athletes on position 3; missing med balls/bands/hurdles switch fillers within the same ladder or pool.

## C4. Standard and Stations
`generatedFormat = 'standard'` generates 2.4.1's sessions (plus Part D). `'stations'` generates the existing stations format with Part 1 together. Home and mobility days are always Standard.

## Part C acceptance criteria (planner §4 "Rack-aware generation," items 2–6, copied exactly)
- [ ] With Rack rotation chosen, every generated weight-room session is Rack rotation: R1 Power, R2 Strength, R3 Secondary, cooldown.
- [ ] Every rotation has ≤ 1 rack position and ≤ 1 barbell position; spotter after barbell squat/bench; no same-muscle filler before the rack lift; rack-lift rest ≥ floors; round 1 is the build-up for tier A/Olympic.
- [ ] The founder's 2-day off-season setup (groups of 4, the 11/18 equipment) generates the §2c Day 1 and Day 2 tables, within 45–60 min at the coach's session length.
- [ ] Groups of 3 and 5 follow §2d.

- [ ] *(Product, D-068.2)* The criterion above is run in a full weight room; in the 11/18 room the same rotations generate with each slot on its own ladder's equipment-fitting rung, and the one-rack/one-bar rule holds.
- [ ] *(Product)* In-season Day 1 Heavy matches the §2c in-season line (about 46 min).
- [ ] *(Product)* Every §7 template (2–5 days, every phase) compiles with no rotation over one rack or one bar position, at all three levels after resolution; R-1, R-2, and R-4 checks pass on rotation sessions.

# PART E · Day-of racks: roll call and confirm (D-069)
**Founder request (11/20):** racks should be assigned from the athletes who are actually present for the workout, and the coach should see the racks and confirm them on the day.
**Founder's choices:** the **coach takes roll call** (athletes don't tap in; no new data about athletes), and it ships **in 2.4.2**.
**Builds on:** rack groups (D-026, `rack-groups.md`, F17/F18), the existing "Who's here today" filter (F17 step 2, never stored), the Part B/C rack sizes (§2d).
**Naming:** the app never calls this "check-in." That word already means the readiness check-in (D-016), which is health data and never drives racks. Use **"Today's racks"** and **"Who's here."**

## E1. When it shows
- On a day with a generated or coach-built **weight-room session** for a team that has rack groups (any format). It's most important for **Rack rotation** and **Stations**, where the day's racks set the rotation.
- Not on home, mobility, break, or testing days. (Testing days keep their own station hint, 2–3 per station.)

## E2. Coach flow ("Today's racks")
1. **Entry:** a "Today's racks" card on the coach's Today on weight-room days, with "Not confirmed yet" or "Confirmed 3:12 PM · 14 here." **Start rotation** and **Start stations** open it first if today's racks aren't confirmed (see E4).
2. **Who's here:** the roster for that session's program, **all checked by default**, with All / None. The coach unticks anyone absent. Athletes who follow another team's program are left out, with the existing note ("2 athletes follow another team's lift program and aren't included. Add them by hand.").
3. **Rebalance (automatic, shown as a preview):** Approach starts from the **current racks** and moves as few athletes as possible:
   1. Remove absent athletes from today's racks.
   2. Place present athletes who aren't in a rack (back after an absence, or new). Each goes back to **the rack they were last in** when it has room (remembered on the coach's device), otherwise to the smallest rack.
   3. **Rack rotation:** every rack ends with **3–5** athletes (§2d). A rack under 3 is closed for today, and its athletes go to the smallest open racks. A rack over 5 gives its extras to the smallest racks. If there are too many athletes for the open racks at 5 each, a closed rack reopens. **Other formats:** rack sizes differ by at most 1 when there are enough athletes; empty racks are hidden for today.
   4. **Who moves:** the balanced-mix rules (D-026). Every rack of 2+ keeps at least one intermediate or advanced athlete where the roster allows, and positions stay spread. **Inputs:** roster, level, position, and today's Who's here list only. Never test results, loads, readiness check-ins, pain, bodyweight, or age.
4. **Preview:** rack columns with board names, coach-only level and position chips (as F17), moved athletes marked "From Rack 2," closed racks shown as "Not used today," and a line such as "14 here · 4 racks · 3 moves." The coach can drag (web) or tap-to-move (phone) anyone, **Shuffle**, or **Use current racks** (no moves).
5. **Confirm racks:** saves to the existing rack groups. Athletes see their rack on Today with the existing "Moved to Rack 3" pill. The board's "Arrange by rack" follows today's racks. Toast: "Racks confirmed. Athletes see their rack on Today."
6. **After confirming:**
   - **Late arrival:** tick them in Today's racks to get "Add Riley to Rack 3?" (the smallest rack under 5), a one-tap add that moves nobody else. Once a rotation is running, they join at the next rotation. A rack of 5 that gets a 6th uses the 5-athlete rule (2 athletes on a non-rack, non-spot position) until the block ends.
   - **Someone leaves:** no change mid-block.
   - **Re-confirm** at any time before Start.

## E3. What it changes in generated sessions
- **Rotations follow each rack's confirmed size** per §2d (3, 4, or 5). Racks on the same day can have different layouts (e.g., Rack 1 at 4 positions, Rack 3 at 3 positions with 2 × rotation rest). Rest floors still hold. This is worked out when the session starts, from the stored session; nothing new is saved per day.
- **Stations:** station time and order use today's number of open racks (`circuits-and-stations.md` Part 2, §4a station formula).
- **Standard:** racks only say where athletes lift; no change to content.

## E4. Never blocks the coach (D-045)
- **Start rotation** / **Start stations** without a confirm today asks once: "Confirm today's racks first?" with **Confirm racks** or **Use current racks**. The existing stations rule stays: stations can't start until everyone present is in a rack.
- If the coach never opens Today's racks, the current racks apply, as in 2.4.1.
- If UX F63 (Start on the coach board) is scheduled, the same one-time prompt applies there.

## E5. Data and privacy
- **No new fields, tables, or keys.** Confirmed racks are written to the existing `rack_groups` / `rack_group_members`, with the existing RLS (only the coach writes) and the existing athlete card and board.
- **Who's here is not stored on the server** and **never written to `attendance`** (F17's rule: "Only used to balance today's racks. Not saved as attendance."). The list and each athlete's last rack stay **on the coach's device** (G-3, like the testing checklist). The Who's here list clears the next day.
- **Absence is never shown** to athletes, teammates, or the board. An athlete left out sees no rack card (the existing unassigned state), with no "absent" label. On the board, an absent athlete who opens the app anyway shows under "Other athletes" (F9b).
- Partner names keep following B5 (the `rack_partner_names` flag).

## Part E acceptance criteria (Product)
- [ ] On a weight-room day with rack groups, the coach's Today shows "Today's racks"; Who's here lists the session's roster, all checked by default, without athletes following another team's program.
- [ ] Unticking absent athletes and rebalancing gives every Rack-rotation rack 3–5 athletes with the fewest moves from the current racks; a rack under 3 is closed for today; returning athletes go back to their last rack when it has room.
- [ ] Rebalance keeps at least one intermediate or advanced athlete in every rack of 2+ when the roster allows, and reads only roster, level, position, and the Who's here list (code review: no reads of `test_results`, loads, `readiness`, or birth year).
- [ ] The preview marks moves and closed racks; the coach can move anyone, shuffle, or keep current racks; Confirm saves to the existing rack tables, and athletes' Today cards and the board update live.
- [ ] A late arrival is added with one tap without moving anyone else; after a rotation has started, they join at the next rotation.
- [ ] Each rack's generated rotations follow its confirmed size per §2d (3/4/5 layouts on the same day), with rack-lift rest ≥ floors; stations time uses today's open racks.
- [ ] Start rotation / Start stations without a confirm asks once (Confirm racks / Use current racks) and never blocks; the stations "everyone present is in a rack" rule still holds.
- [ ] Who's here is never written to the server or to `attendance` (schema diff empty; network check); absence never appears to athletes, teammates, or on the board; no screen uses the word "check-in" for this.
